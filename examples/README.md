# Examples

Every file here is generated by `build_examples.py` from the library itself,
so it doubles as a smoke test:

```bash
python examples/build_examples.py
```

Then try any of them:

```bash
miwear decode-file examples/08_session.hex
miwear legacy  examples/09_legacy_v1.hex
```

| File | Bytes | What it demonstrates |
|---|---|---|
| `01_start_request.hex` | 30 | `CMD_L1START_REQ` with the full 21-byte TLV block |
| `02_start_response.hex` | 30 | the device's reply, note `frx = 1` |
| `03_ack.hex` | 8 | an ACK, empty payload, CRC 0 |
| `04_nak.hex` | 8 | a NAK — same frame, type 0 |
| `05_auth_verify_plain.hex` | 30 | DATA on channel 1 carrying `pyt`/`va0` protobuf |
| `06_multi_write_fragment.hex` | 307 | larger than one 244-byte write — demonstrates why stitching is required |
| `07_encrypted_payload.hex` | 30 | `opcode = 2`, AES-CTR ciphertext |
| `08_session.hex` | 98 | request + response + ACK + auth, decode in one pass |
| `09_legacy_v1.hex` | 16 | `BA DC FE … EF` legacy framing |

## The encrypted sample

`07_encrypted_payload.hex` was produced with:

```
token        = "demo-token"
randomApp    = 11 11 11 11 11 11 11 11 11 11 11 11 11 11 11 11
randomDevice = 22 22 22 22 22 22 22 22 22 22 22 22 22 22 22 22
appKey       = d80d6704719d8aa79e2b3d30eec081ce
```

Reproduce it:

```bash
miwear keys --token 64656d6f2d746f6b656e \
            --app 11111111111111111111111111111111 \
            --dev 22222222222222222222222222222222

# strip the 8-byte L1 header and 2-byte L2 header, then decrypt
miwear decrypt --key d80d6704719d8aa79e2b3d30eec081ce \
               --data 2905b2a3161d869df1ec2ae2bd621149b9751620
```

Expected output — the same protobuf as `05_auth_verify_plain.hex`:

```
plaintext: 080110053a0e7573657269642d6578616d706c65
proto:     [{"field": 1, ... "value": 1}, {"field": 2, ... "value": 5},
            {"field": 7, ... "text": "userid-example"}]
```

That round trip (derive → encrypt → frame → decode → decrypt → protobuf) is
also asserted in `tests/test_protocol.py::TestEndToEnd`.

> These are synthetic frames built to exercise the parser, not recordings from
> a real device. No real tokens or device data appear anywhere in this repo.
